# Public demo

A demo account on the project site that anyone can enter with one button, to try
the application without installing it. Project overview in
[`../general/README.md`](../general/README.md).

## What problem it solves

The site is a showcase: a visitor should see the whole application working, not
a video of it. A real administrator account cannot be shared, and the production
database is the same one the site runs on. The demo gives every visitor an
administrator that can use almost everything, protects what could break the
site, and puts the data back every day.

To see everything with no restriction, install it locally: `pnpm setup:local`
creates a full administrator (root [`README.md`](../../README.md)).

## Who uses it

- **Visitors**: the **«Prueba nuestra demo»** button on the login page signs
  them in as the `demo` user, without a password. It shows only where the
  frontend has `NEXT_PUBLIC_DEMO_MODE=true`.
- **A real administrator** (never the demo account): the **Settings → Demo** tab
  shows the last reset, resets the data by hand and saves the scheduling base.

## What it can do

The demo user is an `admin`, so it sees every module and every screen. It can
create, edit and delete anything the daily reset puts back: logbook entries,
parking bookings, maintenance work orders, groups, cashier shifts, F&B revenue,
invoices, checklists, messages, and it can generate schedules with the solver.

It **cannot**:

| Blocked                                                                    | Where                                                                   |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Create, edit or delete users                                               | `/api/users` (any write) and `POST /api/auth/register`                  |
| Change its own profile, password or avatar                                 | `/api/auth/me/profile`, `/me/password`, `/me/avatar`                    |
| Create, edit or delete departments                                         | `/api/departments` (any write)                                          |
| Change the scheduling configuration, shifts, rules, employees or contracts | `/api/scheduling/{config,shifts,rules,employees,contracts}` (any write) |
| Create backoffice categories                                               | `POST /api/backoffice/categories`                                       |
| Upload any file                                                            | every `multipart/form-data` request                                     |
| See the demo activity log or reset the demo                                | `/api/demo-activity`, `/api/demo`                                       |
| Sign in with a password                                                    | the `demo` account only enters through the button                       |

A blocked request answers `403` with `demo: true`; the frontend shows a «Modo
Demo» notice. Every blocked attempt is stored in `demo_activity_log`.

## What data it handles

- **`users.is_demo = 1`** marks the demo account. The access token carries
  `demo: true` only for that account, and a token refresh reads the flag again
  from the database. The account is created with `pnpm demo:user` (local) or
  `pnpm demo:user:aiven`, with a random password nobody uses.
- **Module data** comes from `backend/db-mysql/mock-data.sql`: fictitious
  records with dates relative to the day of the reset, so the screens never look
  stale.
- **The scheduling base** is a copy of every `scheduling_*` table in
  `demo_snapshot_scheduling_*`: employees, contracts, rules, shifts,
  configuration and the months already generated by the solver.
- **`demo_reset_log`** records each reset and each saved base: when, who (`auto`
  or the administrator), whether it worked and how long it took.

## What rules it follows

### When the data resets

**There is no fixed time.** The reset runs with **the first demo entry of each
day**, counting days in Madrid time:

1. A visitor presses the demo button.
2. The backend looks for the last successful reset in `demo_reset_log`.
3. If it happened today (since 00:00 Madrid), the visitor goes straight in.
   Otherwise the data is reset first, about a second, and then the visitor goes
   in.

So the first visitor of the day always finds clean data, however long the site
has been idle. A session is not reset while it is in use, unless it crosses
midnight and someone else enters the demo.

**Why not a scheduled job at a fixed hour**: the API runs on Render's free plan,
which **puts the service to sleep after 15 minutes without traffic**. A job at,
say, 04:00 would almost always find the service asleep and never run. Resetting
on the first entry works no matter how long the service slept.

An administrator can also reset at any moment from **Settings → Demo**.

### What a reset does

1. Reloads `mock-data.sql`, which empties the module tables and loads the
   fictitious records again. Users, roles, departments and catalogs are not
   touched.
2. Restores the scheduling base from `demo_snapshot_scheduling_*`, inside a
   transaction. If no base was saved, scheduling is left as it is.

Two resets never run at once: a database lock (`GET_LOCK`) makes the second one
answer «busy» (`409`). The reset runs on its own connection, so it does not hold
the application's pool.

### Saving the scheduling base

An administrator generates the months with the solver, as anyone would, and
presses **«Guardar horarios actuales como base»** in Settings → Demo. That
copies every scheduling table into the snapshot tables; from then on each reset
restores that state. Saving again replaces the previous base.

### Limits

Per IP unless stated, and only for the demo account:

| What                                         | Limit                                   |
| -------------------------------------------- | --------------------------------------- |
| Entering the demo                            | 10 per 15 minutes                       |
| Writes (anything but `GET`/`HEAD`/`OPTIONS`) | 60 per 15 minutes                       |
| Generating a schedule with the solver        | 5 per hour per IP, 30 per hour in total |

## How information flows

```
Login page ── POST /api/auth/demo ──► is DEMO_MODE on? (404 if not)
                                     │
                                     ├─ find the is_demo user (503 if none)
                                     ├─ reset already done today (Madrid)?
                                     │     no → reset: mock-data.sql + scheduling base
                                     └─ session cookies, token with demo: true
                                              │
Each request ── authenticateToken ──► demo? multipart → 403
                                     ├─ write rate limit
                                     └─ route guards (denyDemo / denyDemoWrites) → 403
```

Configuration:

| Variable                     | Where    | Effect                                                         |
| ---------------------------- | -------- | -------------------------------------------------------------- |
| `DEMO_MODE=true`             | backend  | Enables `POST /api/auth/demo`, the daily reset and `/api/demo` |
| `NEXT_PUBLIC_DEMO_MODE=true` | frontend | Shows the demo button and the Settings → Demo tab              |

Both are off by default, so a local install has no demo button.
